# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Run locally: `powershell -ExecutionPolicy Bypass -File .\serve.ps1` → opens `http://localhost:8791`. Must be served over HTTP, not opened as `file://` — some browsers restrict `localStorage` on `file://` pages and this app's entire data layer is `localStorage`-backed.
- Regenerate the single-file bundle after editing the multi-file source: `powershell -ExecutionPolicy Bypass -File .\build-bundle.ps1` (see "Two parallel builds" below — this only syncs 4 files, everything else needs hand-editing).
- No package manager, no build step, no linter, no automated test suite — this is a static HTML/CSS/JS prototype with zero dependencies.

## Architecture

**Two parallel builds of the same app — know which one you're editing:**
1. Multi-file source (`pages/*.html` + `assets/js/*.js` + `assets/css/style.css`) — the source of truth; edit here by default.
2. `bundle.html` — a hand-maintained single-file SPA mirror (a router + `<template id="tpl-...">` blocks + named `mountXxx()` functions), used so the app can be opened/shared without a server. `build-bundle.ps1` only auto-syncs `thai-date.js`/`seed-data.js`/`store.js`/`pulse-widget.js` into it. Every page's mount script, `nav.js`, `index.html`'s login script, and every `<template>` must be hand-updated in `bundle.html` whenever the corresponding multi-file source changes — the script's own header comment documents the exact conversion convention (self-executing IIFE → named `mountXxx()`, `*.html`/`?query` links → `#hash` routes + the bundle's shared `getRouteQuery()` helper). Read an existing in-sync template/mount pair as a worked example before adding or updating one.

**Data layer:** `assets/js/store.js` is the single source of truth — a module-pattern IIFE exposing `window.PP` with ~100 functions grouped by entity (teams, milestones, submissions, feedbacks, notifications, gamification/pulse, calendar/workload, etc). All state lives in one `localStorage` key (`projectpulse_state_v1`), loaded/saved via `load()`/`save()`/`commit()`. It auto-reseeds from `assets/js/seed-data.js` whenever `SEED_VERSION` doesn't match — bump that constant whenever seed data changes meaningfully so existing browsers remigrate cleanly.

**Page convention:** every page in `pages/` loads scripts in the same order — `thai-date.js → seed-data.js → store.js → nav.js → <script>PPNav.mount("<page-key>")</script> → <page-specific>.js` — and shares the same shell: `#appShell > #appBody > .app-main > .app-main__inner#pageContent`. Content isn't templated or server-rendered; each page-specific JS file renders template strings into empty containers by ID at runtime.

**Navigation:** `assets/js/nav.js` injects the header/sidebar/bottom-nav/footer into every page via `PPNav.mount(activeKey)`. There is one unified 6-item nav (`NAV_ITEMS`: Dashboard/Projects/Review Queue/Calendar/Notifications/Profile — same items for both roles, per-role hrefs). Pages not among those 6 (e.g. `task-detail.html`, `team-workload.html`, `settings.html`) still call `mount()` with their own key, which resolves through `ACTIVE_KEY_ALIAS` to highlight the nearest parent nav item rather than getting their own sidebar entry.

**Access control is role-based, not route-based:** there's no server, so there's no real auth/authorization boundary. Every page-specific JS file opens with a `PP.getCurrentUser().role !== "..."` guard that hides content and shows a redirect link when the wrong role is viewing it. Switching identity (`PP.setRole`/`setCurrentTeam`/`setCurrentAdvisor`) is just a client-side `localStorage` write via the header's "Demo" user-switcher — treat any role check as UI convenience, not a security boundary.

**Project Pulse status system:** `PP.computeHealthScore(teamId)` returns a 4-level `level` (`'dormant'|'weak'|'steady'|'strong'`, worst→best) derived from a single 0–100 score with deductions for lateness/inactivity/blocked status/risk/deadline collisions/workload imbalance (thresholds: `<55` dormant, `<78` weak, `<90` steady, else strong; also exposed as `statusTier` 0–3 / Thai `statusLabel` on the same return object). `assets/js/pulse-widget.js`'s `RHYTHM_META` keys match this 4-value scheme 1:1 — there is no separate rhythm-mapping layer. Every UI surface showing Pulse pairs icon + color + text label, never color alone — reuse the exact `PULSE_LEVEL_META` object already duplicated in `dashboard-student.js`/`dashboard-advisor.js`/`project-detail.js` rather than inventing new copy.

**Milestones and phases (two different, unrelated "6 phases"):** all teams share a fixed 10-step milestone template (`STATE.milestoneDefs`, same order for every team, with project-type-specific name/subtask overrides in `seed-data.js`'s `MILESTONE_TEMPLATE_OVERRIDES`). `store.js`'s `PP.getProjectPhases()`/`PHASE_DEFS` groups them into 6 phases for its own internal "phase timeline" naming (Research/Storyboard-Planning/Prototype/Production/Testing/Presentation). Separately, `pages/project-detail.html`'s Milestones & Timeline tab uses its own local `MILESTONE_TO_PHASE`/`SPEC_PHASES` mapping (in `assets/js/project-detail.js`) to relabel the same 10 milestones into the product spec's 6 phase names (Pre-production/Production/Post-production/Revision/Submission/Completion). These two groupings are intentionally independent — don't assume they line up, and don't edit one expecting it to affect the other.

**CSS is one token-driven file** (`assets/css/style.css`, all `--pp-*` custom properties on `:root`). Several tokens are read directly from JS as inline style strings (e.g. `pulse-widget.js` and the dashboard files reference `var(--pp-green-600)`/`var(--pp-red-700)` etc. by exact name) — grep `--pp-` across `assets/js/` before renaming or removing any token. Status colors (green/amber-yellow/orange/red) are reserved for the 4 Pulse levels only; every other accent uses the neutral/ink scale (`--pp-navy-*`/`--pp-purple-*` — despite the names, these are a charcoal/warm-ink palette now, not literal navy/purple; the names were kept to avoid a repo-wide rename).

**Firebase/Firestore is a disconnected experiment**, not the app's data layer: `assets/js/firebase-config.js`, `seed-firestore.html`, and `firestore-teams.html` exist at the repo root but no page under `pages/` loads or references them. `localStorage` via `store.js` is the sole real source of truth for the running app.

## Firestore (experimental, disconnected from the app)

- Collections actually seeded today by `seed-firestore.html`: **`advisors`** (3 docs) and **`teams`** (5 docs) — confirmed live via the screenshot in `docs/firestore-console.png`.
- If this ever gets wired into the real app, the full collection set implied by `store.js`'s in-memory model would be: `course`, `courseSettings`, `advisors`, `teams`, `students`, `milestones`, `submissions`, `feedbacks`, `otherCourseTasks`, `schedule`, `personalBlocks`, `freeTimeSuggestions`, `notifications`, `checkins`, `pulsePoints`, `weeklyMomentum`. None of these exist in Firestore yet beyond `advisors`/`teams`.
- Closest 3-state "pending → approved/rejected" workflow in this app (the same shape as a leave-request's รอพิจารณา/อนุมัติ/ไม่อนุมัติ): a `submission.status` of `submitted` (awaiting advisor review) resolves, via `PP.giveFeedback()`, into a `feedback.decision` of `passed` (approved) or `revise`/`need_info` (sent back). There's no single field with exactly those 3 literal values — `submitted` lives on the submission, `passed`/`revise`/`need_info` on the feedback it produces.
- **Project prohibition — do not commit real secrets.** `assets/js/firebase-config.js` is already tracked in git and pushed to the public GitHub repo (`opongpangs-star/ProjectPulse2`). Its `apiKey` is a Firebase **client-side web config** — Google's own docs say this is safe to expose publicly, unlike a server secret or an Admin SDK service-account key (never commit one of those). The real gate is **Firestore Security Rules**, not hiding this file — check the Rules tab in the Firebase Console (project `projectpulse2-eb313`) before trusting this project with anything beyond demo data, since there's no rules file in this repo to confirm what's currently enforced.
