# ACL — Advisor Change Requests

Access control for the Firestore-backed **Advisor Change Requests** feature (`pages/advisor-change-new.html`, `pages/advisor-change-list.html`, collection `advisorChangeRequests`). This is a separate identity system from the main app's `localStorage` demo-login — access here is governed by a real signed-in Firebase Authentication account and its `role` field in the `users/{uid}` Firestore document (`"student"` by default at sign-up, `"advisor"` set manually in the Firebase Console).

| Role | Can do | Cannot do |
|---|---|---|
| **student** | Sign up / sign in / log out. Create a new advisor-change request (team, new advisor, reason — becomes a record with `status: "pending"` and `createdByUid` set to their own uid). View the list of **their own** requests only. Delete **their own** requests, but only while `status` is still `"pending"`. | Cannot approve or decline **any** request, including their own — status changes are advisor-only, with no exception for the request's own creator. Cannot view, delete, or otherwise act on another student's requests. Cannot edit any field of a request after creation (team, advisor selection, reason are permanently fixed at creation — only `status`/`decidedAt` can ever change, and never by a student). Cannot delete a request once it's been approved or declined. |
| **advisor** | Sign in / log out. View **all** advisor-change requests (see note below). Approve or decline any request that is still `"pending"` — this writes only the `status` and `decidedAt` fields, nothing else. | Cannot create a new advisor-change request (creation is student-only). Cannot delete any request, at any status. Cannot edit any field of a request other than `status`/`decidedAt` — reason, team, and advisor-selection fields are never advisor-editable. Cannot change the status of a request that's already been decided (no re-approving or un-declining). |

**Known gap (deliberate, not yet built):** advisor accounts aren't linked to a specific advisor record in Firestore's `advisors` collection, so "all requests" above really does mean *all* — an advisor can approve/decline a request addressed to a different advisor. Properly scoping this to "only requests addressed to *me*" needs an account-to-advisor-record link, which is out of scope for this pass (matches the same "real enforcement lives in security rules, week 8" boundary called out in the main course worksheet).
