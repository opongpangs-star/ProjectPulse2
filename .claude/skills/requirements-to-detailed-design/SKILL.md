# Skill: → Detailed Design (Conceptual, ProjectPulse)

Skill นี้รันอยู่ใน main conversation (ไม่ใช่ subagent) เพราะต้อง**ถามผู้ใช้และรอคำตอบ**หลายจุดก่อนลงมือเขียนเอกสารจริง ห้ามข้ามขั้นตอนถามยืนยันแม้ผู้ใช้จะรีบหรือดูมั่นใจก็ตาม — sequence flow ที่เขียนผิดลำดับหรือพลาด edge case จะถูกยึดเป็นสเปกไปพัฒนาต่อ แก้ทีหลังจะกระทบงานที่ implement ไปแล้ว

## เมื่อไหร่ควรใช้ Skill นี้

- ผู้ใช้ขอให้สร้างเอกสาร detailed design ระดับ conceptual (ไม่ผูกกับ implementation ปัจจุบัน) พร้อม sequence flow จาก `SPEC.md`/`DATA_MODEL.md`/`ARCHITECTURE.md`/`CONCEPTUAL_DATA_MODEL.md`/`CONCEPTUAL_API_SPEC.md` ที่มีอยู่ (ทั้งระบบ หรือระบุเจาะจงเฉพาะ scenario/operation)
- มีหน้า/operation ใหม่เข้ามา แล้วต้องการเพิ่ม sequence flow ให้ครอบคลุม
- ผู้ใช้ขอปรับปรุงเอกสาร `DETAILED_DESIGN.md` ที่มีอยู่แล้ว

**ไม่ใช่** สำหรับการแก้ implementation จริง (ไฟล์ใน `pages/`/`assets/`) หรือแก้ `SPEC.md`/`DATA_MODEL.md` เอง

**หมายเหตุ:** โปรเจกต์นี้ไม่ได้ใช้ git จึงไม่มีขั้นตอน sync/commit/PR — งานที่เขียนจะอยู่เป็นไฟล์ในเครื่องทันที

## หลักการสำคัญ (บังคับใช้ทุกครั้ง)

1. **เสนอแผนก่อนสร้างเสมอ** — ห้ามเขียนเอกสารก่อนผู้ใช้ยืนยันแผน (ขั้นตอนที่ 5)
2. **ทุกจุดที่ไม่ชัดเจน ต้องเสนออย่างน้อย 3 ทางเลือกพร้อมข้อดี/ข้อเสีย** ให้ผู้ใช้ตัดสินใจผ่าน `AskUserQuestion` เสมอ ห้ามเดาเงียบ ๆ แล้วเขียนไปเลย (ดูรายการจุดที่ต้องถามในขั้นตอนที่ 1–4)
3. **ห้ามผูกเอกสารนี้กับ implementation ปัจจุบัน** — ห้ามใส่ localStorage, ชื่อฟังก์ชัน `PP.*`, ชื่อไฟล์/CSS class ลงในเอกสาร conceptual ที่กำลังสร้าง
4. **Sequence Flow ต้องมีเสมอต่อ scenario** — ไม่ว่าจะเลือก notation แบบไหนก็ตาม (ขั้นตอนที่ 4(ก))
5. **ทุก scenario ต้องอ้างอิง operation ที่มีนิยามอยู่แล้วใน `CONCEPTUAL_API_SPEC.md` หรือ `SPEC.md`** — ห้ามแต่ง scenario ที่ไม่มีสเปกรองรับ

## ขั้นตอนการทำงาน

### 1. ตรวจสอบเอกสารต้นทางที่จำเป็นต้องมีก่อน

Detailed design ต้องอ้างอิงชื่อ component/entity/operation ที่นิยามไว้แล้ว ไม่ใช่ตั้งใหม่เอง จึงอยากมีอย่างน้อย:
- `ARCHITECTURE.md` (conceptual component)
- `CONCEPTUAL_API_SPEC.md` (operation ที่จะแตกเป็น sequence flow)
- `SPEC.md` (edge case ที่จะแตกเป็น alternate/error flow — มีอยู่แล้วในโปรเจกต์นี้เสมอ)

ถ้า `ARCHITECTURE.md`/`CONCEPTUAL_API_SPEC.md` ยังไม่มี ให้ถามผู้ใช้ผ่าน `AskUserQuestion`:
- **รัน skill ที่เกี่ยวข้องก่อน** (แนะนำ) — `requirements-to-architecture` และ/หรือ `requirements-to-data-api-spec` ก่อนเริ่มงานนี้ เพื่อให้ sequence flow อ้างอิงชื่อที่นิยามไว้แล้วจริง ไม่ต้องเดา แต่ใช้เวลาเพิ่มอีกรอบ
- **ใช้ `SPEC.md` เป็นแหล่งอ้างอิงตรงไปเลย** — เร็วกว่า ไม่ต้องรอ แต่ agent จะต้อง "ตั้งชื่อชั่วคราว" ให้ component/operation ที่อาจไม่ตรงกับที่เอกสาร conceptual อื่นจะนิยามไว้จริงทีหลัง ต้องมาไล่แก้ให้ตรงกันอีกครั้ง
- **ทำเฉพาะ scenario ที่มีข้อมูลอ้างอิงพร้อมแล้วไปก่อน** ส่วนที่ยังขาดให้ข้ามไว้เป็น open question

### 2. กำหนดขอบเขต (Scope)

ถ้าผู้ใช้ระบุแล้ว (เช่น "ทำ detailed design เฉพาะ flow ส่งงานตรวจ") → ใช้ตามนั้น ไม่ต้องถามซ้ำ

ถ้าผู้ใช้บอกกว้าง ๆ ("ทำ detailed design ให้หน่อย") → ถามผ่าน `AskUserQuestion`:
- **ครอบคลุมทุก operation/scenario ที่มีอยู่ตอนนี้** — เห็นภาพสมบูรณ์ที่สุด เหมาะเป็นครั้งแรกที่สร้างเอกสารนี้ แต่ใช้เวลานานและเอกสารจะยาวมาก (โปรเจกต์นี้มี 14 หน้า มี flow ค่อนข้างมาก)
- **เฉพาะฟีเจอร์/operation ที่ผู้ใช้ระบุ** — เร็วกว่า เหมาะเมื่อมีฟีเจอร์ใหม่เข้ามาหรือต้องการโฟกัสจุดที่ยังไม่ชัด
- **เฉพาะ scenario ที่มีความเสี่ยงสูง** (เช่น การให้ Feedback/อนุมัติ Milestone ที่ต้องเป็นดุลยพินิจอาจารย์เท่านั้น, การมอบหมายงานที่ไม่สมดุล) — ใช้เวลาน้อยที่สุด โฟกัสจุดที่คุ้มค่าที่สุด แต่ scenario อื่นจะไม่มี sequence flow ให้อ้างอิง

### 3. ตรวจสอบว่าเป็นของใหม่หรือมีของเดิม

ตรวจดูว่ามีไฟล์ `DETAILED_DESIGN.md` อยู่แล้วหรือไม่

**ถ้ายังไม่มี** — เป็นการสร้างเอกสารใหม่ทั้งหมด ข้ามไปขั้นตอนที่ 4 ได้เลย

**ถ้ามีอยู่แล้ว** — อ่านเพื่อดู scenario ที่เขียนไว้แล้ว แล้วถามผู้ใช้ผ่าน `AskUserQuestion` ว่าต้องการ **เพิ่ม scenario ใหม่ต่อจากของเดิม** (แนะนำเมื่อของเดิมยังใช้ได้ ไม่ต้องแก้) หรือ **ทบทวน scenario เดิมที่มีอยู่ด้วย** (แนะนำเมื่อ operation/entity ที่ scenario เดิมอ้างถึงถูกแก้ไขในเอกสาร conceptual อื่นไปแล้ว)

### 4. จุดที่มักไม่ชัดเจน — ต้องถามพร้อม ≥3 ทางเลือกเสมอ

ก่อนเสนอแผนในขั้นตอนที่ 5 ให้ตรวจสอบว่าผู้ใช้ระบุสิ่งต่อไปนี้ชัดเจนแล้วหรือยัง ถ้ายัง ให้ถามผ่าน `AskUserQuestion`:

**(ก) Sequence Diagram Notation (บังคับ)**
1. **Mermaid `sequenceDiagram`** — render เป็นภาพได้จริงถ้าเปิดผ่าน renderer ที่รองรับ Mermaid (โปรเจกต์นี้มี `.obsidian/` อยู่แล้ว), มีสัญลักษณ์ message/lifeline มาตรฐาน เหมาะกับ flow ที่มีนิสิต/อาจารย์/ระบบสลับกันทำงาน แต่ raw text อ่านยากกว่าถ้าไม่มี renderer
2. **ASCII arrow-based textual sequence** (เช่น `นิสิต -> การติดตาม Milestone: ส่งงานเข้าคิวตรวจ` ทีละบรรทัด) — อ่านได้ทันทีไม่ต้องมี renderer แต่ flow ที่แตกสาย/วนซ้ำจะอ่านตามยากกว่าภาพ
3. **ตาราง step-by-step** (คอลัมน์: # / ต้นทาง / action / ปลายทาง / ผลลัพธ์) — จัดระเบียบดี ใส่รายละเอียดต่อ step ได้มาก แต่เห็นภาพรวมการสลับไปมาระหว่าง component ได้ไม่ชัดเท่า diagram

**(ข) ระดับความละเอียดของ Flow (บังคับ)**
1. **Happy path เท่านั้น** — เขียนเร็วที่สุด แต่จะไม่มีสเปกสำหรับ error/edge case ที่ `SPEC.md` ระบุไว้แล้วหลายจุด (เช่น เงื่อนไข disable ฟอร์มตอนรอตรวจ)
2. **Happy path + error/alternate flow หลัก ๆ** — ครอบคลุมเคสที่พบบ่อย/สำคัญ บาลานซ์ระหว่างความครบถ้วนกับเวลาที่ใช้
3. **ครบทุก edge case ที่ระบุไว้ใน `SPEC.md`** — ครบที่สุด แต่เอกสารจะยาวและใช้เวลาเขียน/ดูแลรักษานานกว่า 2 แบบข้างต้นมาก

**(ค) ขอบเขตการครอบคลุม (บังคับ)**
1. **ต่อ operation** (1 sequence flow ต่อ 1 operation ใน `CONCEPTUAL_API_SPEC.md`/`SPEC.md`) — จัดระเบียบชัดเจน ตรวจสอบครบทุก operation ได้ง่าย แต่ operation ที่ต้องเกิดต่อกันจริง (เช่น ส่งงาน → เข้าคิว → แจ้งเตือนอาจารย์) จะถูกแยกเป็นเอกสารคนละที่
2. **ต่อ Scenario การใช้งานต่อเนื่อง** (1 sequence flow ครอบคลุมหลาย operation ต่อกัน เช่น วงจร submit→review→feedback-to-task ทั้งหมด) — เห็นภาพการใช้งานจริงต่อเนื่อง แต่ operation ที่ถูกใช้ซ้ำในหลาย scenario จะถูกอธิบายซ้ำหลายที่
3. **เฉพาะ scenario ที่ต้องลงรายละเอียดจริง ๆ** (เช่น เฉพาะจุดที่มีการตัดสินใจซับซ้อน/สิทธิ์เฉพาะบทบาท) — ประหยัดเวลาที่สุด แต่ scenario ง่าย ๆ ที่ไม่ได้เขียนไว้จะไม่มีเอกสารอ้างอิงเลย

ถ้าผู้ใช้ตอบมาแล้วในคำสั่งแรกอย่างชัดเจนสำหรับข้อไหน ไม่ต้องถามซ้ำข้อนั้น — ถามเฉพาะข้อที่ยังไม่ชัด

### 5. เสนอแผน (Plan Proposal) — รอ confirm ก่อนเขียนเอกสารจริง

สรุปแผนเป็นข้อความสั้น ๆ ประกอบด้วย:

- ขอบเขต scenario/operation ที่จะครอบคลุม
- การตัดสินใจจากขั้นตอนที่ 1 (เอกสารต้นทางพร้อมหรือยัง), ขั้นตอนที่ 3 (สร้างใหม่/เพิ่ม/ทบทวนของเดิม), และขั้นตอนที่ 4 (notation, ระดับความละเอียด, ขอบเขตการครอบคลุม)
- รายการ scenario คร่าว ๆ ที่คาดว่าจะปรากฏในเอกสาร
- สมมติฐาน/คำถามเปิดที่เจอระหว่างอ่านเอกสาร (ถ้ามี ให้ถามผู้ใช้ก่อน)

จบด้วยคำถามยืนยันชัดเจน เช่น "ยืนยันแผนนี้เพื่อเริ่มเขียน `DETAILED_DESIGN.md` ใช่หรือไม่ หรือต้องการปรับส่วนไหนก่อน?" แล้ว**รอผู้ใช้ตอบรับก่อนไปขั้นตอนถัดไป**

### 6. ลงมือเขียน — เรียก subagent `detailed-design-doc-writer`

เมื่อผู้ใช้ยืนยันแผนแล้ว ให้เรียกใช้ agent `detailed-design-doc-writer` (ผ่าน Agent tool) พร้อมส่งข้อมูลที่สรุปไว้ในขั้นตอนที่ 5 ให้ครบ: scenario/operation ที่จะครอบคลุม, การตัดสินใจเรื่อง notation/ระดับความละเอียด/ขอบเขตการครอบคลุม, และว่าเป็นการสร้างใหม่/เพิ่ม/ทบทวนของเดิม

ถ้า agent รายงานกลับมาว่าเจอจุดที่ไม่ชัดเจนระหว่างเขียน ให้นำคำถามนั้นมาถามผู้ใช้ต่อ (พร้อมอย่างน้อย 3 ทางเลือก+ข้อดีข้อเสีย) ก่อนเรียก agent ต่อให้ทำงานจนจบ — ห้ามเดาแทน agent

### 7. สรุปผล

หลัง agent เขียนเสร็จ สรุปให้ผู้ใช้ทราบว่า: ไฟล์ `DETAILED_DESIGN.md` ถูกสร้าง/แก้ไขที่ path ไหน, scenario ที่ครอบคลุม, และมีอะไรที่ยังเป็น open question/สมมติฐานที่ต้องตรวจสอบต่อ (ถ้ามี)
