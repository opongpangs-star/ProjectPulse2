# Skill: SPEC/Data Model → Conceptual Data Model & API Spec (ProjectPulse)

Skill นี้รันอยู่ใน main conversation (ไม่ใช่ subagent) เพราะต้อง**ถามผู้ใช้และรอคำตอบ**หลายจุดก่อนลงมือเขียนเอกสารจริง ห้ามข้ามขั้นตอนถามยืนยันแม้ผู้ใช้จะรีบหรือดูมั่นใจก็ตาม — entity/relationship/operation ที่ตั้งชื่อผิดทิศตั้งแต่ต้น จะกระทบความเข้าใจภาพรวมของทั้งทีมในระยะยาว

## เมื่อไหร่ควรใช้ Skill นี้

- ผู้ใช้ขอให้สร้างเอกสาร data model (entity/attribute/relationship + ER diagram) และ/หรือ API spec ระดับ conceptual (ไม่ผูกกับ implementation ปัจจุบัน) จาก `SPEC.md`/`DATA_MODEL.md` ที่มีอยู่ (ทั้งระบบ หรือระบุเจาะจงเฉพาะ entity/หน้า)
- มีหน้า/ฟีเจอร์ใหม่เข้ามาใน `SPEC.md`/`DATA_MODEL.md` แล้วต้องการขยาย/ปรับ data model หรือ api spec เดิมให้ครอบคลุม
- ผู้ใช้ขอปรับปรุงเอกสาร `CONCEPTUAL_DATA_MODEL.md` หรือ `CONCEPTUAL_API_SPEC.md` ที่มีอยู่แล้ว

**ไม่ใช่** สำหรับการแก้ `SPEC.md`/`DATA_MODEL.md` เอง หรือแก้ไฟล์ implementation จริงใน `pages/`/`assets/` — skill นี้แค่อ่านเอกสารเหล่านั้นเพื่อสรุปเป็นภาพรวม conceptual เท่านั้น

**หมายเหตุ:** โปรเจกต์นี้ไม่ได้ใช้ git จึงไม่มีขั้นตอน sync/commit/PR — งานที่เขียนจะอยู่เป็นไฟล์ในเครื่องทันที

## หลักการสำคัญ (บังคับใช้ทุกครั้ง)

1. **เสนอแผนก่อนสร้างเสมอ** — ห้ามเขียนเอกสารก่อนผู้ใช้ยืนยันแผน (ขั้นตอนที่ 4)
2. **ทุกจุดที่ไม่ชัดเจน ต้องเสนออย่างน้อย 3 ทางเลือกพร้อมข้อดี/ข้อเสีย** ให้ผู้ใช้ตัดสินใจผ่าน `AskUserQuestion` เสมอ ห้ามเดาเงียบ ๆ แล้วเขียนไปเลย (ดูรายการจุดที่ต้องถามในขั้นตอนที่ 1–3)
3. **ห้ามผูกเอกสารนี้กับ implementation ปัจจุบัน** — ห้ามใส่ localStorage, ชื่อฟังก์ชัน `PP.*`, object shape ของ JS จริง ลงในเอกสาร conceptual ที่กำลังสร้าง (เก็บไว้ที่ `DATA_MODEL.md` เดิม)
4. **ER Diagram ต้องมีเสมอในเอกสาร data model** — ไม่ว่าจะเลือก notation แบบไหนก็ตาม (ขั้นตอนที่ 3(ก))
5. **ทุก entity/operation ต้องอ้างอิง `SPEC.md`/`DATA_MODEL.md` จริงที่มีอยู่** — ห้ามแต่ง entity/operation ที่ไม่มีสเปกรองรับ

## ขั้นตอนการทำงาน

### 1. กำหนดขอบเขต (Scope)

ถามตัวเองก่อนว่าผู้ใช้ระบุขอบเขตชัดแล้วหรือยัง — มี 2 มิติที่ต้องชัดเจนก่อนไปต่อ:

**(ก) จะทำเอกสารไหน**

ถ้าผู้ใช้ไม่ได้ระบุ ให้ถามผ่าน `AskUserQuestion`:
- **ทำทั้ง Data Model + API Spec พร้อมกัน** (แนะนำ) — สอดคล้องกันแน่นอนเพราะเขียนจาก entity ชุดเดียวกัน แต่ใช้เวลามากกว่า
- **ทำเฉพาะ Data Model** — เหมาะเมื่อยังไม่แน่ใจเรื่อง operation/flow แต่ต้องการเห็นภาพข้อมูลก่อน
- **ทำเฉพาะ API Spec** — เหมาะเมื่อมี data model ที่พอใช้ได้อยู่แล้ว (เช่นใน `DATA_MODEL.md`) และแค่ต้องการนิยาม operation ระดับแนวคิดเพิ่ม

**(ข) ขอบเขตเนื้อหา**

- ถ้าผู้ใช้ระบุแล้ว (เช่น "ทำ data model ครอบคลุมทั้งระบบที่มีอยู่ตอนนี้") → ใช้ตามนั้น ไม่ต้องถามซ้ำ
- ถ้าผู้ใช้บอกกว้าง ๆ → ถามผ่าน `AskUserQuestion` โดยเสนอตัวเลือก:
  - **ครอบคลุมทุก entity/operation ใน `DATA_MODEL.md`/`SPEC.md` ตอนนี้** — เห็นภาพสมบูรณ์ที่สุด เหมาะเป็นครั้งแรกที่สร้างเอกสารนี้ แต่ใช้เวลาอ่านเอกสารทั้งหมด
  - **เฉพาะกลุ่ม entity ที่ผู้ใช้ระบุ** (เช่น เฉพาะ Milestone/Submission/Feedback) — เร็วกว่า เหมาะเมื่อมีฟีเจอร์ใหม่เข้ามาและเอกสารเดิมมีอยู่แล้ว
  - **ระบุ entity/resource เจาะจงเอง** — ให้ผู้ใช้พิมพ์ชื่อ entity/resource ที่ต้องการ เหมาะเมื่อต้องการโฟกัส/ทบทวนจุดเดียว

อ่าน `SPEC.md`, `DATA_MODEL.md` ตามขอบเขตที่เลือก และเช็คว่ามี `ARCHITECTURE.md` อยู่แล้วหรือไม่ (ถ้ามี อ่านเพื่อใช้ชื่อ conceptual component จัดกลุ่ม entity/resource ให้สอดคล้อง — ถ้ายังไม่มี ไม่บังคับต้องมีก่อน แต่แจ้งผู้ใช้ว่า entity/resource ที่จะได้อาจจัดกลุ่มไม่ตรงกับภาพรวมถ้าทำ `ARCHITECTURE.md` ทีหลัง)

### 2. ตรวจสอบว่าเป็นของใหม่หรือมีของเดิม

ตรวจดูว่ามีไฟล์ `CONCEPTUAL_DATA_MODEL.md` และ/หรือ `CONCEPTUAL_API_SPEC.md` อยู่แล้วหรือไม่ (เช็คแยกตามขอบเขตที่เลือกในขั้นตอนที่ 1(ก))

**ถ้ายังไม่มี** — เป็นการสร้างเอกสารใหม่ทั้งหมด ข้ามไปขั้นตอนที่ 3 ได้เลย

**ถ้ามีอยู่แล้ว** — อ่านเพื่อดู entity/resource ที่ตั้งชื่อไว้แล้ว แล้วถามผู้ใช้ผ่าน `AskUserQuestion` ว่าต้องการ:
  - **ขยาย/ปรับปรุงเอกสารเดิมในที่เดิม** — *แนะนำเมื่อ*: เป็นการเพิ่ม entity/operation ใหม่ที่ไม่ทำให้ของเดิมเปลี่ยนความหมาย — ข้อดี: ไม่มีของซ้ำซ้อน / ข้อเสีย: ถ้าโครง entity เดิมไม่เหมาะกับของใหม่ อาจต้องรื้อบางส่วน
  - **ทบทวนโครงสร้างใหม่ทั้งหมด (major revision)** — *แนะนำเมื่อ*: ฟีเจอร์ใหม่ทำให้แนวคิดการแบ่ง entity/resource เดิมไม่เหมาะสมแล้ว — ข้อดี: เอกสารสอดคล้องกับความต้องการจริงมากขึ้น / ข้อเสีย: กระทบลิงก์/การอ้างอิงจากเอกสารอื่นที่อาจอ้าง entity เดิมไปแล้ว

### 3. จุดที่มักไม่ชัดเจน — ต้องถามพร้อม ≥3 ทางเลือกเสมอ

ก่อนเสนอแผนในขั้นตอนที่ 4 ให้ตรวจสอบว่าผู้ใช้ระบุสิ่งต่อไปนี้ชัดเจนแล้วหรือยัง (เฉพาะข้อที่เกี่ยวกับขอบเขตที่เลือกในขั้นตอนที่ 1) ถ้ายัง ให้ถามผ่าน `AskUserQuestion`:

**(ก) ER Diagram Notation (บังคับถ้าขอบเขตรวม Data Model)**
1. **Mermaid `erDiagram`** — render เป็นภาพได้จริงถ้าเปิดผ่าน Obsidian (โปรเจกต์นี้มี `.obsidian/` อยู่แล้ว) หรือ renderer ที่รองรับ Mermaid, มีสัญลักษณ์ cardinality มาตรฐาน แต่ raw text อ่านยากกว่าถ้าไม่มี renderer
2. **ASCII text diagram** — อ่านได้ทันทีไม่ต้องมี renderer แต่ปรับ layout ที่มี entity จำนวนมากได้ยาก
3. **ตารางความสัมพันธ์แบบข้อความ** (เช่น "1 ทีมมีได้หลาย Milestone") ไม่มีภาพ — เขียน/แก้เร็วที่สุด แต่เห็นภาพรวมความสัมพันธ์ทั้งหมดพร้อมกันได้ยากกว่ามีภาพ

**(ข) ระดับความละเอียดของ Attribute (บังคับถ้าขอบเขตรวม Data Model)**
1. **Minimal** — มีแค่ entity + ความสัมพันธ์หลัก ไม่ลง attribute ละเอียด — เร็ว เหมาะระยะเริ่มคิดภาพรวม
2. **Medium** — attribute + ชนิดข้อมูลระดับแนวคิด + จำเป็น/ไม่จำเป็น — บาลานซ์ดี พอให้ผู้อ่านเข้าใจโครงสร้างจริงโดยไม่ต้องเดามาก
3. **Full** — เพิ่ม uniqueness/ค่าเริ่มต้น/สถานะ lifecycle ของ attribute ด้วย (เช่น 10 สถานะมาตรฐานของ Milestone) — ครบสุด แต่เขียน/ดูแลรักษานานกว่า

**(ค) รูปแบบการเขียน API Spec (บังคับถ้าขอบเขตรวม API Spec)**
1. **Resource + Operation table แบบ CRUD-style** — จัดกลุ่มตาม resource ก่อน แล้วลิสต์ operation ในแต่ละ resource — อ่านง่าย ครอบคลุมเป็นระบบ แต่มองไม่เห็น flow ข้าม resource ในหน้าเดียว
2. **จัดกลุ่มตาม Scenario การใช้งาน** (เช่น วงจร submit→review→feedback-to-task, วงจรจัดสรรเวลาว่าง) — เห็น flow ชัดเจนตรงกับการใช้งานจริง แต่ operation ที่ถูกใช้ซ้ำในหลาย scenario อาจถูกพูดถึงซ้ำหลายที่
3. **Contract-style ละเอียดต่อ operation** — ละเอียดพร้อมใช้อ้างอิงเวลาต้อง implement ต่อ แต่เขียนนานและยาวกว่า 2 แบบข้างต้นมาก

ถ้าผู้ใช้ตอบมาแล้วในคำสั่งแรกอย่างชัดเจนสำหรับข้อไหน ไม่ต้องถามซ้ำข้อนั้น — ถามเฉพาะข้อที่ยังไม่ชัดและเกี่ยวกับขอบเขตที่เลือกจริง ๆ

### 4. เสนอแผน (Plan Proposal) — รอ confirm ก่อนเขียนเอกสารจริง

สรุปแผนเป็นข้อความสั้น ๆ ประกอบด้วย:

- ขอบเขต (data model/api spec/ทั้งสอง + entity ที่ครอบคลุม)
- การตัดสินใจจากขั้นตอนที่ 2 (สร้างใหม่/ขยายของเดิม/ทบทวนใหม่) และขั้นตอนที่ 3 (ER notation, ระดับความละเอียด attribute, รูปแบบ API spec)
- รายการ entity/resource ระดับแนวคิดคร่าว ๆ ที่คาดว่าจะปรากฏในเอกสาร
- สมมติฐาน/คำถามเปิดที่เจอระหว่างอ่านเอกสาร (ถ้ามี ให้ถามผู้ใช้ก่อน)

จบด้วยคำถามยืนยันชัดเจน เช่น "ยืนยันแผนนี้เพื่อเริ่มเขียนเอกสารใช่หรือไม่ หรือต้องการปรับส่วนไหนก่อน?" แล้ว**รอผู้ใช้ตอบรับก่อนไปขั้นตอนถัดไป**

### 5. ลงมือเขียน — เรียก subagent `data-api-doc-writer`

เมื่อผู้ใช้ยืนยันแผนแล้ว ให้เรียกใช้ agent `data-api-doc-writer` (ผ่าน Agent tool) พร้อมส่งข้อมูลที่สรุปไว้ในขั้นตอนที่ 4 ให้ครบ: ขอบเขตที่จะทำ (data model/api spec/ทั้งสอง), การตัดสินใจเรื่อง ER notation/ระดับความละเอียด attribute/รูปแบบ API spec, และว่าเป็นการสร้างใหม่หรือขยาย/ทบทวนของเดิม

ถ้า agent รายงานกลับมาว่าเจอจุดที่ไม่ชัดเจนระหว่างเขียน (เช่น `SPEC.md`/`DATA_MODEL.md` ขัดแย้งกันเอง) ให้นำคำถามนั้นมาถามผู้ใช้ต่อ (พร้อมอย่างน้อย 3 ทางเลือก+ข้อดีข้อเสีย) ก่อนเรียก agent ต่อให้ทำงานจนจบ — ห้ามเดาแทน agent

### 6. สรุปผล

หลัง agent เขียนเสร็จ สรุปให้ผู้ใช้ทราบว่า:
- ไฟล์ไหนถูกสร้าง/แก้ไขบ้าง (`CONCEPTUAL_DATA_MODEL.md`/`CONCEPTUAL_API_SPEC.md`)
- entity/resource ที่ครอบคลุม
- open question/สมมติฐานที่ยังต้องตรวจสอบต่อ (ถ้ามี)

## Output ที่คาดหวัง

- `CONCEPTUAL_DATA_MODEL.md` (ไฟล์ root ของโปรเจกต์) — Conceptual Data Model (entity, attribute ระดับแนวคิด, ความสัมพันธ์, ER Diagram, Open Questions, ลิงก์ไปยัง `DATA_MODEL.md`) — ถ้าขอบเขตรวม Data Model
- `CONCEPTUAL_API_SPEC.md` (ไฟล์ root ของโปรเจกต์) — Conceptual API Spec (resource, operation, input/output ระดับแนวคิด, การอ้างอิงสเปกต้นทาง, Open Questions, ลิงก์ไปยัง `DATA_MODEL.md`) — ถ้าขอบเขตรวม API Spec
