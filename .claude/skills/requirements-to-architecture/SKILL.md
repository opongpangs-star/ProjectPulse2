# Skill: SPEC/Data Model → High-Level Architecture (ProjectPulse)

Skill นี้รันอยู่ใน main conversation (ไม่ใช่ subagent) เพราะต้อง**ถามผู้ใช้และรอคำตอบ**หลายจุดก่อนลงมือเขียนเอกสารจริง ห้ามข้ามขั้นตอนถามยืนยันแม้ผู้ใช้จะรีบหรือดูมั่นใจก็ตาม — เอกสารนี้เป็นชั้นแนวคิดที่จะถูกอ้างอิงต่อไปอีกนาน แก้ทิศทางผิดจะกระทบความเข้าใจภาพรวมของทั้งทีม

## เมื่อไหร่ควรใช้ Skill นี้

- ผู้ใช้ขอให้สร้างเอกสาร high-level architecture ระดับ conceptual (ไม่ผูกกับวิธี implement ปัจจุบัน) จาก `SPEC.md`/`DATA_MODEL.md` ที่มีอยู่ (ทั้งระบบ หรือระบุเจาะจงเฉพาะหน้า/flow)
- มีหน้า/ฟีเจอร์ใหม่เข้ามาใน `SPEC.md` แล้วต้องการขยาย/ปรับเอกสาร architecture เดิมให้ครอบคลุม
- ผู้ใช้ขอปรับปรุงเอกสาร `ARCHITECTURE.md` ที่มีอยู่แล้ว

**ไม่ใช่** สำหรับการแก้ `SPEC.md`/`DATA_MODEL.md` เอง หรือแก้ไฟล์ implementation จริงใน `pages/`/`assets/` — skill นี้แค่อ่านเอกสารเหล่านั้นเพื่อสรุปเป็นภาพรวม conceptual เท่านั้น

**หมายเหตุ:** โปรเจกต์นี้ไม่ได้ใช้ git (ตรวจสอบแล้วว่าไม่มี `.git`) จึงไม่มีขั้นตอน sync/commit/PR เหมือน skill ในโปรเจกต์อื่น — งานที่เขียนจะอยู่เป็นไฟล์ในเครื่องทันที

## หลักการสำคัญ (บังคับใช้ทุกครั้ง)

1. **เสนอแผนก่อนสร้างเสมอ** — ห้ามเขียนเอกสารก่อนผู้ใช้ยืนยันแผน (ขั้นตอนที่ 3)
2. **ทุกจุดที่ไม่ชัดเจน ต้องเสนออย่างน้อย 3 ทางเลือกพร้อมข้อดี/ข้อเสีย** ให้ผู้ใช้ตัดสินใจผ่าน `AskUserQuestion` เสมอ ห้ามเดาเงียบ ๆ แล้วเขียนไปเลย (ดูรายการจุดที่ต้องถามในขั้นตอนที่ 2)
3. **ห้ามผูกเอกสารนี้กับ implementation ปัจจุบัน** — ห้ามใส่ localStorage, ชื่อฟังก์ชัน `PP.*`, ชื่อไฟล์ `.html`/`.js`, ชื่อ CSS class ลงในเอกสาร architecture ที่กำลังสร้าง (เก็บรายละเอียดเหล่านั้นไว้ที่ `DATA_MODEL.md`/`SPEC.md` เดิม)
4. **data flow ทุกเส้นต้องอ้างอิง scenario จริงที่มีอยู่ใน `SPEC.md`** — ถ้าพบว่า `SPEC.md` ไม่ครอบคลุมหน้า/flow ที่ผู้ใช้ต้องการ ต้องแจ้งผู้ใช้ก่อนเดินหน้า ไม่สมมติ flow ขึ้นมาเอง

## ขั้นตอนการทำงาน

### 1. กำหนดขอบเขต (Scope)

ถามตัวเองก่อนว่าผู้ใช้ระบุขอบเขตชัดแล้วหรือยัง:

- ถ้าผู้ใช้ระบุแล้ว (เช่น "ทำ architecture doc ครอบคลุมทั้งระบบที่มีอยู่ตอนนี้") → ใช้ตามนั้น ไม่ต้องถามซ้ำ
- ถ้าผู้ใช้บอกกว้าง ๆ ("ทำเอกสาร architecture ให้หน่อย") → ใช้ `AskUserQuestion` ถามขอบเขต โดยเสนอตัวเลือก:
  - **ครอบคลุมทุกหน้า/scenario ใน `SPEC.md` ตอนนี้** — เห็นภาพรวมสมบูรณ์ที่สุด เหมาะเป็นครั้งแรกที่สร้างเอกสารนี้ แต่ใช้เวลาอ่าน `SPEC.md` ทั้งหมด (14 หน้า)
  - **เฉพาะกลุ่ม flow ที่ผู้ใช้ระบุ** (เช่น เฉพาะวงจร submit → review → feedback-to-task) — เร็วกว่า เหมาะเมื่อมีฟีเจอร์ใหม่เข้ามาและเอกสาร architecture เดิมมีอยู่แล้ว
  - **ระบุหน้า/ฟังก์ชันเจาะจงเอง** — ให้ผู้ใช้พิมพ์ชื่อหน้า/ฟีเจอร์ที่ต้องการ เหมาะเมื่อต้องการโฟกัสเฉพาะ data flow เส้นหนึ่งที่มีปัญหา/ต้องทบทวน

อ่าน `SPEC.md` และ `DATA_MODEL.md` ให้ครบตามขอบเขตที่เลือกก่อนไปขั้นตอนถัดไป และเช็คว่ามี `ARCHITECTURE.md` อยู่แล้วหรือไม่ (ด้วย Glob/Read)

**ถ้ายังไม่มี `ARCHITECTURE.md`** — เป็นการสร้างใหม่ทั้งหมด ข้ามไปขั้นตอนที่ 2 ได้เลย

**ถ้ามีอยู่แล้ว** — อ่านเพื่อดูโครงสร้าง/component ที่ตั้งชื่อไว้แล้ว แล้วถามผู้ใช้ผ่าน `AskUserQuestion` ว่าต้องการ:
  - **ขยาย/ปรับปรุงเอกสารเดิมในที่เดิม** — *แนะนำเมื่อ*: เป็นการเพิ่มหน้า/flow ใหม่ที่ไม่ทำให้ component เดิมเปลี่ยนความหมาย — ข้อดี: ไม่มีของซ้ำซ้อน / ข้อเสีย: ถ้าโครงเดิมไม่เหมาะกับของใหม่ อาจต้องรื้อบางหัวข้อ
  - **ทบทวนโครงสร้างใหม่ทั้งหมด (major revision)** — *แนะนำเมื่อ*: หน้า/flow ใหม่ทำให้แนวคิดการแบ่ง component เดิมไม่เหมาะสมแล้ว — ข้อดี: เอกสารสอดคล้องกับระบบจริงมากขึ้น / ข้อเสีย: ใช้เวลามากกว่าเพราะต้องอ่านทวนทั้งหมด

### 2. จุดที่มักไม่ชัดเจน — ต้องถามพร้อม ≥3 ทางเลือกเสมอ

ก่อนเสนอแผนในขั้นตอนที่ 3 ให้ตรวจสอบว่าผู้ใช้ระบุสิ่งต่อไปนี้ชัดเจนแล้วหรือยัง ถ้ายัง ให้ถามผ่าน `AskUserQuestion`:

**(ก) ระดับความละเอียดของ Component (granularity)**
1. **Coarse-grained** (3–4 บล็อกใหญ่ เช่น "มุมมองนิสิต" / "มุมมองอาจารย์" / "ชั้นข้อมูลกลาง" / "ระบบแจ้งเตือน") — เข้าใจง่ายเร็ว เหมาะสื่อสารภาพรวมกับผู้ที่ไม่ใช่สายเทคนิค แต่ไม่ละเอียดพอให้แบ่งงานพัฒนาต่อ
2. **Medium-grained แยกตามความรับผิดชอบหลัก** (เช่น "การติดตาม Milestone", "วงจร Feedback/Review", "การจัดสรรเวลา/ภาระงาน", "การแจ้งเตือนและรายงาน") — บาลานซ์ดี ตรงกับกลุ่มหน้าใน `SPEC.md` อยู่แล้ว ใช้แบ่งงานได้จริง แต่ต้องดูแลรักษาโครงสร้างนี้ให้ทันเมื่อมีฟีเจอร์ใหม่
3. **Fine-grained แยกทุกหน้า/ฟังก์ชันย่อย** — ครบและแม่นยำที่สุด ใกล้เคียงจำนวนหน้าจริง (14 หน้า) แต่จะดูรกเกินจำเป็นสำหรับเอกสารภาพรวมระดับ architecture

**(ข) รูปแบบการนำเสนอ Diagram**
1. **ASCII text diagram** — อ่านได้ทันทีไม่ต้องมี renderer แต่ปรับ layout ที่มี component จำนวนมากได้ยาก
2. **Mermaid diagram** (Obsidian ในโปรเจกต์นี้ render เป็นภาพได้ เพราะมีโฟลเดอร์ `.obsidian/` อยู่แล้ว) — ดูเป็นภาพสวยกว่า จัดการ flow ที่ซับซ้อนง่ายกว่า แต่ต้องเปิดผ่าน renderer ที่รองรับ Mermaid ถึงจะเห็นภาพ
3. **ตารางขั้นตอน ไม่มีภาพ diagram** — เขียนเร็วที่สุด ไม่มีปัญหาเรื่อง renderer แต่เห็นภาพรวม component ทั้งหมดพร้อมกันได้ยากกว่ามีภาพ

**(ค) ขอบเขต Non-functional ที่จะรวมในเอกสาร**
1. **ไม่รวม non-functional เลย** เก็บเฉพาะ component + data flow — เอกสารสั้น โฟกัสชัด
2. **รวมแบบหลักการกว้าง ๆ** (เช่น "ต้องรองรับหลายทีม/หลายอาจารย์พร้อมกันได้โดยไม่ปนข้อมูลกัน", "การแจ้งเตือนควรถึงผู้ใช้ทันทีหลังเกิดเหตุการณ์") — ให้ context ที่เป็นประโยชน์โดยไม่ตัวเลขจำเพาะเจาะจงเกินไป
3. **รวมแบบละเอียดมีเกณฑ์ชัดเจน** (อ้างอิงเป้าหมายการทดลองใช้ที่มีอยู่แล้วใน `SPEC.md`/`weekly-report` เช่น Milestone ครบ ≥70%, ส่งตรงเวลา ≥80%, รอ Feedback ไม่เกิน 7 วัน) — มีประโยชน์มากถ้าจะใช้เอกสารนี้ประเมินผลจริง แต่เสี่ยงเอาเกณฑ์เฉพาะการทดลองรอบนี้มาปนกับหลักการ architecture ที่ควรเป็นกลางกว่านั้น

ถ้าผู้ใช้ตอบมาแล้วในคำสั่งแรกอย่างชัดเจนสำหรับข้อไหน ไม่ต้องถามซ้ำข้อนั้น — ถามเฉพาะข้อที่ยังไม่ชัด

### 3. เสนอแผน (Plan Proposal) — รอ confirm ก่อนเขียนเอกสารจริง

สรุปแผนเป็นข้อความสั้น ๆ ประกอบด้วย:

- ขอบเขต/หน้า-flow ที่จะครอบคลุม
- การตัดสินใจจากขั้นตอนที่ 1 (สร้างใหม่/ขยายของเดิม/ทบทวนใหม่) และขั้นตอนที่ 2 (granularity, diagram style, ขอบเขต non-functional)
- รายการ component ระดับ conceptual คร่าว ๆ ที่คาดว่าจะปรากฏในเอกสาร (ยังไม่ต้องเขียนละเอียด แค่ชื่อ+หน้าที่สั้น ๆ ให้ผู้ใช้เห็นภาพก่อน)
- สมมติฐาน/คำถามเปิดที่เจอระหว่างอ่าน `SPEC.md`/`DATA_MODEL.md` (ถ้ามี ให้ถามผู้ใช้ก่อน)

จบด้วยคำถามยืนยันชัดเจน เช่น "ยืนยันแผนนี้เพื่อเริ่มเขียน `ARCHITECTURE.md` ใช่หรือไม่ หรือต้องการปรับส่วนไหนก่อน?" แล้ว**รอผู้ใช้ตอบรับก่อนไปขั้นตอนถัดไป**

### 4. ลงมือเขียน — เรียก subagent `architecture-doc-writer`

เมื่อผู้ใช้ยืนยันแผนแล้ว ให้เรียกใช้ agent `architecture-doc-writer` (ผ่าน Agent tool) พร้อมส่งข้อมูลที่สรุปไว้ในขั้นตอนที่ 3 ให้ครบ: ขอบเขต, การตัดสินใจเรื่อง granularity/diagram style/non-functional scope, และว่าเป็นการสร้างใหม่หรือขยาย/ทบทวนของเดิม

ถ้า agent รายงานกลับมาว่าเจอจุดที่ไม่ชัดเจนระหว่างเขียน (เช่น `SPEC.md` ขัดแย้งกันเอง, flow ที่จำเป็นไม่มีสเปกรองรับ) ให้นำคำถามนั้นมาถามผู้ใช้ต่อ (พร้อมอย่างน้อย 3 ทางเลือก+ข้อดีข้อเสีย) ก่อนเรียก agent ต่อให้ทำงานจนจบ — ห้ามเดาแทน agent

### 5. สรุปผล

หลัง agent เขียนเสร็จ สรุปให้ผู้ใช้ทราบว่า:
- ไฟล์ `ARCHITECTURE.md` ถูกสร้าง/แก้ไขที่ path ไหน
- component/scenario ที่ครอบคลุม
- open question/สมมติฐานที่ยังต้องตรวจสอบต่อ (ถ้ามี)

---

## Output ที่คาดหวัง

- `ARCHITECTURE.md` (ไฟล์ root ของโปรเจกต์) — เอกสาร High-Level Architecture ระดับ conceptual (System Context, Conceptual Components, Data Flow ตาม Scenario, หลักการเชิง architecture, Non-functional Considerations ตามขอบเขตที่เลือก, Open Questions, ลิงก์ไปยัง `DATA_MODEL.md`)
